이 문서는 사용자가 지정한 [영상](https://www.youtube.com/watch?v=MpkwqNDz-qk)을 계기로 작성한 기획 초안입니다. 확보한 것은 영상 제목 메타데이터와 일부 페이지 셸이며, 영상·음성·자막 본문은 확보하지 못했습니다. 따라서 **영상의 발언을 하나하나 검토했다거나, 아래 열 가지 불편이 해당 영상에서 관찰되었다고 주장하지 않습니다.** 타임스탬프를 붙인 관찰은 0건이고, 전체 구간 검토율은 산정할 수 없습니다.

현재 산출물은 기존 코드의 한계와 공개된 과거 사례를 출발점으로 한 제품 가설, 유스케이스, 검증 설계입니다. 영상 근거를 확보하면 이 가설에 억지로 끼워 맞추지 않고, 실제 발언을 별도로 분절해 채택·수정·폐기해야 합니다. 이 문서 추가는 기능 구현, 사용자 수요 검증, 출시 또는 기존 PR의 병합을 뜻하지 않습니다.

## 제품 판단

첫 대상으로 가정하는 사용자는 협업·제작·홍보 의뢰를 이메일로 받는 1인 운영자와 소규모 팀입니다. 김선태 본인이나 특정 회사가 Naruon의 고객이라는 뜻이 아닙니다. 과거 보도에서 확인되는 것은 광고와 응원 등이 섞인 메일이 다수 도착했다는 사례뿐입니다. 그 사례를 이번 영상의 현재 업무량이나 모든 창작자의 공통 문제로 일반화하지 않습니다. 근거의 범위는 아래 E02에 명시했습니다.

Naruon이 줄여야 할 일은 메일 본문을 읽는 시간만이 아닙니다. 서로 다른 스레드에서 같은 의뢰의 조건을 찾고, 무엇이 바뀌었는지 비교하고, 누가 다음 답변을 해야 하는지 기억하고, 합의한 내용을 작업으로 다시 옮기는 일입니다. 이 연결이 유효한지는 사용자 검증이 필요합니다.

권고하는 제품 단위는 **원문 근거에 연결된 ‘의뢰’와 ‘미해결 약속’**입니다. 메일은 그대로 고객의 공급자에 남겨 두고, Naruon이 의뢰별 맥락·변경·답변 책임·다음 행동을 연결합니다. 장문의 새 요약을 읽게 하기보다, 지금 결정할 한 가지와 그 근거를 먼저 보여 줍니다.

| 접근 | 장점 | 이 기획에서의 판단 |
| --- | --- | --- |
| 메일별 분류·요약 강화 | 기존 메일 화면에 붙이기 쉽습니다. | 스레드 사이 조건 변경과 미해결 책임을 남겨 두므로 보조 기능으로만 씁니다. |
| 별도의 영업 CRM 구축 | 거래 단계를 넓게 표현할 수 있습니다. | 초기 사용자가 별도 원장을 관리하게 하고 회계·영업 기능까지 범위가 커집니다. 이번 범위에서 제외합니다. |
| 기존 워크스페이스 안의 의뢰·약속 연결 | 메일·관계·작업·일정을 판단 단위로 연결합니다. | 권고안입니다. 먼저 외부 쓰기 없는 수신 의뢰 화면으로 가설을 검증합니다. |

기존 [플랫폼 기획](../naruon-platform-plan.md)의 맥락 종합, 예외 수정, 약속 강도 구분, 사적 맥락의 최소 공개 원칙을 유지합니다. 이미 가진 정보는 사용자가 재입력하게 하지 않습니다. 근거가 부족하면 자동으로 확정하지 않고 잠정 제안 또는 보류로 표시합니다. 상대에게 추가 정보가 필요한 경우에는 기존 자료로 먼저 채운 뒤, 실제로 빠진 항목만 묻는 답장 초안을 만듭니다. 이는 사용자에게 장문의 분류 설문을 요구하는 방식과 다릅니다.

## 첫 범위와 우선순위

**P0: 수신 의뢰의 판단 준비.** UC01의 의뢰 후보 목록, UC03의 근거·누락 정보, UC04의 ‘내 답변 필요’를 묶습니다. UC02에서는 읽기 전용 관련 스레드 제안까지만 포함합니다. 사용자는 원문과 근거를 확인하고, 잘못된 제안을 되돌리며, 답장 초안까지 준비할 수 있습니다. 원본 메일의 이동·삭제, 외부 발송, 계약 수락, 일정 예약은 하지 않습니다.

첫 구현 슬라이스는 이보다 작게, 동의한 단일 사용자·단일 워크스페이스의 선택된 메일 소스에서 **수신 의뢰 후보와 판단 근거를 읽기 전용으로 보여 주는 것**입니다. 외부 LLM이 없으면 근거 조회는 유지하되 생성·추론 불가 상태를 밝힙니다. 없는 추론 결과를 채워 넣지 않습니다.

**P1: 합의 이후의 실행 연결.** UC05의 조건 변경, UC06의 일정 대조, UC07의 자료 근거, UC09의 내부 작업 연결을 검증합니다. 공동 작업 UC08은 권한·책임 배정 검증 후에만 엽니다. UC10은 수요가 확인된 뒤 후속 자료 제출 추적으로 좁혀 도입합니다. 결제 처리나 회계 원장은 만들지 않습니다.

이 우선순위는 시장 규모나 발생 빈도를 측정한 결과가 아닙니다. P0는 기존 메일·작업 화면과 가깝고, 외부 행동 없이 틀린 제안의 비용을 제한할 수 있다는 설계 판단입니다. 영상에 더 직접적이고 중요한 불편이 확인되면 우선순위를 바꿉니다.

## 의뢰·약속·실행 상태를 섞지 않습니다

| 축 | 제안 상태 | 의미와 종료 조건 |
| --- | --- | --- |
| 의뢰 결정 | `unreviewed`, `needs_information`, `under_review`, `accepted`, `declined`, `closed` | 검토·수락·거절의 사업적 판단입니다. 메일을 읽거나 초안을 만든 것만으로 수락·종료되지 않습니다. |
| 응답 책임 | `awaiting_us`, `awaiting_counterparty`, `no_response_due`, `needs_review` | 개별 질문·약속별 다음 응답 주체입니다. 한 의뢰 안에 양방향 책임이 동시에 존재할 수 있습니다. |
| 약속 강도 | `desired`, `tentative`, `confirmed` | 희망·가예약·확정을 구분합니다. 제안만으로 확정 약속을 덮어쓰지 않습니다. |
| 외부 실행 | `not_requested`, `prepared`, `submitted`, `confirmed`, `failed`, `unknown` | 이후 외부 쓰기가 도입될 때 사용합니다. 초안 생성·접수·전송 확인은 서로 다릅니다. 타임아웃은 성공도 실패 확정도 아닙니다. |

부재중 자동 회신이나 접수 알림이 도착해도 실질 질문이 해결되었다고 자동 종료하지 않습니다. 명시적인 취소·충족 근거 또는 사용자의 수정으로 닫고, 새 요청이나 모순되는 후속 자료가 오면 해당 책임을 재검토합니다. 기존 7일 후보 조회는 보조 신호일 뿐, 열린 의뢰의 삭제·종료 기준이 아닙니다.

## 개념 모델과 처리 경계

다음은 **제안 개념**이지 적용된 DB 마이그레이션이나 공개 API 계약이 아닙니다.

- `inquiry_cases`: `case_uid`, `case_title`, `decision_state`, `case_revision`과 범위 식별자.
- `response_obligations`: `obligation_uid`, `case_uid`, `responsibility_state`, `responsible_actor_uid`, `due_at`, `completion_evidence_uid`.
- `case_evidence_links`: `evidence_uid`, `case_uid`, `source_uid`, `source_record_uid`, `source_revision`, `evidence_locator`, `observed_at`.
- `case_decision_records`: `decision_uid`, `case_uid`, `decision_kind`, `decision_reason`, `input_revision`, `decided_at`.

각 객체는 조직·워크스페이스·소유 또는 위임 범위를 가집니다. 외부 메시지 식별자는 소스 범위 안에서만 해석합니다. 참조 대상도 같은 범위인지 서버가 검증하며, 표시 제목·이메일 도메인·맨 식별자만으로 조인하지 않습니다. 브라우저에는 불투명한 공개 UID만 전달합니다. 새 DB 이름은 의미 있는 두 단어 이상 `snake_case`, Python 함수·필드는 `snake_case`, TypeScript 변수·함수는 `camelCase`, 타입·클래스·컴포넌트는 `PascalCase`로 구분합니다. 기존 공급자 프로토콜 필드를 일괄 개명하지 않습니다.

처리 순서는 권한 확인 → 허용된 원문·버전의 짧은 읽기 → 트랜잭션과 연결 반환 → 추론·비교 → 버전 재확인 → 짧은 조건부 저장입니다. **LLM·외부 API·장시간 계산 중 DB 트랜잭션이나 명시적 락을 유지하지 않습니다.** 동시에 다른 사람이 수정했으면 `case_revision`에 대한 비교 후 갱신으로 충돌을 알리고 다시 계산합니다. 재시도와 작업 점유가 필요하면 짧은 점유 트랜잭션과 만료 가능한 임대를 검토하고, 외부 I/O 동안 행 잠금을 잡는 방식을 승인한 것으로 해석하지 않습니다.

Naruon은 의뢰 맥락, 사용자 판단, 작업 연결을 담당합니다. 자격증명은 Keyverse의 출시된 계약을 통해 연결하는 방향이며, 아직 소비 가능한 계약이 없으면 새 외부 연동을 비활성화합니다. `.env`나 직접 공급자 호출을 우회 경로로 추가하지 않습니다. LLM 라우팅은 contextual-orchestrator의 계약, 문서·음성 처리는 해당 구성요소의 출시된 capability를 확인해 소비합니다. 다른 서비스의 DB를 직접 조회하거나 열린 PR의 소스를 복사하지 않습니다.

## 안전·개인정보·운영

접근 허용 여부는 검색·근거 구성·LLM 전달·초안 작성·실행 시 각각 재검증합니다. 동일 조직이라도 다른 워크스페이스의 메일이나 이전 고용주의 자료를 자동으로 합치지 않습니다. 개인 일정은 동의한 최소 결과인 ‘해당 시간 불가’만 업무 문맥에 전달하며 사유를 노출하지 않습니다. 유사한 이름이나 같은 도메인이 동일 인물·동일 계약이라는 근거가 되지 않습니다.

메일·첨부의 지시문은 데이터입니다. 외부 본문이 다른 계정 검색, 파일 업로드, 비밀정보 조회, 승인 생략을 지시해도 실행 권한을 부여하지 않습니다. 원문·자격증명·주소록을 로그나 텔레메트리에 넣지 않습니다. 보존 기간과 삭제 요청은 원문뿐 아니라 파생 근거·검색 인덱스·초안에도 전파합니다. 감사 기록에 보존해야 할 최소 항목은 별도 정책으로 정의합니다.

소스별 마지막 동기화·조회 범위·연결 실패·미파싱 첨부를 표시합니다. `없음`, `조회하지 못함`, `권한 없음`, `검토 필요`를 같은 빈 화면으로 표현하지 않습니다. 처리 예산·취소·대기열을 두되 숫자는 실제 공급자와 작업 크기 측정으로 정합니다. 이 문서는 임의의 처리량·정확도·절감률을 약속하지 않습니다.

## 근거 목록과 해석 범위

**E01 — 지정 영상.** YouTube, 「김선태 홍보」로 반환된 메타데이터. [원본](https://www.youtube.com/watch?v=MpkwqNDz-qk). 조회일 2026-09-11. 추출 메타데이터는 같은 날짜를 반환했으나 업로드 일시·전체 길이·발언 본문은 원본으로 독립 검증하지 못했습니다. 재생 불가 응답과 추천 영상이 섞인 페이지 셸은 발언 근거가 아닙니다.

**E02 — 별도의 과거 보도.** 박다영. (2026. 3. 6.). 「대박 난 김선태 “구독자 100만, 잠 못 자...광고 포함 메일 700개”」. 머니투데이. [기사](https://www.mt.co.kr/society/2026/03/06/2026030621380612515). 해당 기사는 다른 영상의 발언을 다루며, 광고·응원 등이 섞인 메일 사례를 보도합니다. 지정 영상의 대본, 현재 메일 수, 700건 전부가 광고라는 근거로 사용하지 않습니다.

**E03 — 직접 읽은 코드.** [reply_tracking_service.py](https://github.com/ContextualWisdomLab/naruon/blob/042b0c70531b229af3acbd0421a2f23098d848b3/backend/services/reply_tracking_service.py), blob `a8933848c48f3e4520c541ee64bdb0b5340d8bec`. `detect_reply_tracking`, `thread_reply_candidate`, `check_missing_replies`, `configured_email_addresses`를 확인했습니다. 소스 구조에 대한 근거이며 런타임 성능·악용 가능성을 실증한 결과는 아닙니다.

**E04 — 저장소 기능·경계 문서.** [README](https://github.com/ContextualWisdomLab/naruon/blob/042b0c70531b229af3acbd0421a2f23098d848b3/README.md)의 North-star scope 및 Agentic Ontology 절. 문서에 기재된 기능과 의도이며 이 작업의 실환경 검증 결과가 아닙니다.

**E05 — 상위 기획.** [플랫폼 기획](https://github.com/ContextualWisdomLab/naruon/blob/042b0c70531b229af3acbd0421a2f23098d848b3/docs/planning/naruon-platform-plan.md), blob `7e93ecbd212770ed877cc3bc867deec5c6640392`. CP-1~CP-5와 상태 구분을 적용합니다. 문서 안의 과거 기준 SHA와 LIVE 라벨은 별도 재검증 대상입니다.

**E06 — 인간-AI 상호작용 연구.** Amershi, S., Weld, D., Vorvoreanu, M., Fourney, A., Nushi, B., Collisson, P., Suh, J., Iqbal, S., Bennett, P. N., Inkpen, K., Teevan, J., Kikin-Gil, R., & Horvitz, E. (2019). Guidelines for human-AI interaction. *Proceedings of the 2019 CHI Conference on Human Factors in Computing Systems*. [DOI](https://doi.org/10.1145/3290605.3300233), [저자 기관 페이지](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/). 인간-AI 설계 지침과 평가를 제시한 연구입니다. 여기서는 오류 시 동작·수정 가능성의 설계 검토 배경으로 참고하며, Naruon의 효과를 입증하는 연구로 제시하지 않습니다. PDF 재배포 권한을 확인하지 않아 원문 파일은 추가하지 않았습니다.

**E07 — 개발 경계.** [AGENTS.md](https://github.com/ContextualWisdomLab/naruon/blob/042b0c70531b229af3acbd0421a2f23098d848b3/AGENTS.md)의 범위·식별자·공급자 쓰기·STM·비밀정보 경계를 확인했습니다. 새로운 외부 계약의 존재나 출시를 추정하는 데 사용하지 않습니다.
