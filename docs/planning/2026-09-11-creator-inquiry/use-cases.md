## UC01 — 오늘 판단할 의뢰를 고릅니다

**사용자와 시작 조건.** 승인된 메일 소스가 있는 1인 운영자에게 새 메일이 동기화됩니다. 원본 계정의 권한과 조회 범위를 먼저 확인합니다.

**흐름.** Naruon은 단순 수신 시간순 목록과 구별되는 ‘판단할 의뢰’ 보기를 제안합니다. 각 항목에는 의뢰 목적, 명시된 기한, 필요한 다음 판단, 그 판단을 뒷받침하는 원문을 붙입니다. 기한이 없으면 없는 것으로 표시하며, 유명 기업·광고비 추정치로 중요도를 자동 확정하지 않습니다. 사용자가 이미 설정한 선호·제약은 근거가 유효한 범위에서 적용합니다. 틀린 분류는 한 번의 수정으로 되돌릴 수 있습니다.

**결과와 제외.** 의뢰 후보가 검토 가능해지지만 메일은 이동·삭제되지 않습니다. 응원 메일을 자동 폐기하거나 자동 거절하지 않습니다. 다른 화면에서 숨긴 의뢰도 해당 권한 범위의 전체 목록에서 찾을 수 있어야 합니다.

**실패와 검증.** 연결 실패·부분 동기화·모델 실패는 ‘의뢰 없음’과 구별합니다. 한국어·영어·혼합 언어를 각각 평가합니다. E02는 혼합 메일 상황의 역사적 배경일 뿐 정확한 의뢰 분류 수요의 검증은 아닙니다. 재사용 후보 E04, 새 기능은 수신 의뢰 판단 보기입니다. 수용 기준: AT01, AT02, AT12, AT15.

## UC02 — 여러 메일을 한 의뢰의 맥락으로 읽습니다

**사용자와 시작 조건.** 같은 협업과 관련 있어 보이는 새 스레드가 도착합니다. 브랜드가 같거나 제목이 비슷하다는 사실만으로 동일 의뢰라고 판단할 수는 없습니다.

**흐름.** Naruon은 스레드 참조·원문에서 명시한 프로젝트 관계·소스 범위와 버전을 함께 검토해 연결을 제안합니다. 기존 대화에서 해소되는 정보는 사용자에게 다시 묻지 않습니다. 불확실한 연결은 잠정 표시하고, 사용자 수정으로 연결을 해제할 수 있게 합니다. 서로 다른 계약의 메시지는 별개의 원문과 의뢰로 유지합니다.

**결과와 제외.** 관련 원문을 함께 볼 수 있어 맥락을 다시 모으는 일을 줄일 수 있다는 가설입니다. 원본 메일을 합치거나 지우는 파괴적 dedupe는 없습니다. 동일 발신 도메인만으로 기존 가격·개인 메일·다른 프로젝트 조건을 끌어오지 않습니다.

**실패와 검증.** 같은 브랜드의 별도 캠페인, 같은 제목의 다른 의뢰, 전달된 사본, 다른 소스에서 충돌한 Message-ID를 검증합니다. 기존 관계·스레드 기능 E04는 재사용 후보이며 의뢰 간 연결 계약은 새 설계입니다. 수용 기준: AT03, AT04, AT12, AT16.

## UC03 — 답장 전에 빠진 조건과 모순을 드러냅니다

**사용자와 시작 조건.** 협업 요청에 일부 조건만 적혀 있습니다. 예를 들어 합성 메일에 ‘다음 달 촬영을 제안합니다’라고만 적혀 있다면 확정 촬영일이 존재하는 것이 아닙니다.

**흐름.** 읽을 수 있는 허용된 원문에서 의뢰 목적·산출물·희망 일정·명시 예산·승인 주체 등 판단에 필요한 항목을 채웁니다. 모든 분야에 같은 양식을 강요하지 않고 의뢰 유형별 필수 정보 정책을 버전 관리합니다. 각 필드에는 근거가 붙고, 충돌하는 값은 덮어쓰지 않습니다. 실제로 없는 정보만 묻는 한 개의 답장 초안을 제안합니다. 원문에 이미 있는 내용을 사용자에게 재입력하게 하지 않습니다.

**결과와 제외.** 사용자가 검토할 수 있는 조건표와 질문 초안이 생깁니다. 누락 예산을 업계 평균으로 채우거나 계약 조건을 새로 만들어 넣지 않습니다. 초안은 발송이 아니며 MVP는 외부 발송을 하지 않습니다.

**실패와 검증.** 첨부를 인식하지 못했다면 ‘해당 자료 미확인’을 표시합니다. 사적 가격 정보가 다른 문맥에서 넘어오지 않게 하고 초안 생성 후 원문이 바뀌면 재검토합니다. E05의 맥락 종합 원칙을 적용한 새 유스케이스입니다. 수용 기준: AT05, AT10, AT12, AT13, AT16.

## UC04 — ‘내 답변 필요’와 ‘상대 답변 대기’를 구별합니다

**사용자와 시작 조건.** 받은 의뢰를 읽었지만 아직 답하지 않았거나, 내가 상대에게 보낸 질문의 답을 기다립니다. 한 의뢰 안에 양쪽 상태가 함께 존재할 수 있습니다.

**흐름.** Naruon은 개별 질문·약속과 책임 주체를 연결하고, ‘내 답변 필요’와 ‘상대 답변 대기’를 따로 표시합니다. 읽음·별표·초안 작성은 응답 완료 신호가 아닙니다. 약속한 기한의 출처를 보여 주고, 명시 기한이 없으면 사용자 정책의 목표와 상대가 합의한 기한을 구별합니다. 장기 미해결 항목은 조회 창 밖으로 밀려나도 열린 상태를 유지합니다.

**결과와 제외.** 오늘 해야 할 답변과 추적할 기다림이 구별됩니다. 기존 `pending-replies`와 `reply_sla`는 발신 대기의 후보 기반으로만 사용하며 수신 의뢰 완료 판단으로 둔갑시키지 않습니다.

**실패와 검증.** 물음표 없는 한국어 요청, 부분 답변, 부재중·접수 알림, 7일을 넘긴 미해결 건, 소스 일부만 동기화된 상태를 검증합니다. E03으로 기존 기능과의 차이를 직접 확인했습니다. 수용 기준: AT06, AT07, AT08, AT15.

## UC05 — 조건이 바뀌었을 때 무엇을 다시 결정할지 보여 줍니다

**사용자와 시작 조건.** 후속 메일에서 산출물 수·기한·배포 범위 등의 조건이 달라집니다.

**흐름.** Naruon은 원래 조건, 새 제안, 합의 여부를 필드별로 나란히 제시합니다. ‘새 메일이므로 확정’이라고 덮어쓰지 않고 아직 동의하지 않은 조건을 분리합니다. 변경이 영향을 주는 작업·일정에는 재검토 사유와 근거를 연결합니다.

**결과와 제외.** 사용자는 전체 대화를 다시 읽기보다 달라진 조건과 다음 결정을 봅니다. 법적 효력 판정, 계약서 확정, 기존 확정 약속의 자동 취소는 범위 밖입니다.

**실패와 검증.** 서로 모순되는 자료, 잘못된 연결, 누락된 첨부, 동시 수정은 보류 또는 충돌로 표시합니다. E05의 약속 강도 원칙을 적용하며 조건 버전 비교는 새 설계입니다. 수용 기준: AT09, AT10, AT11, AT16.

## UC06 — 가능한 일정인지 근거를 대조합니다

**사용자와 시작 조건.** 의뢰에 촬영·회의·제출 희망 시간이 있고, 사용자가 일정 대조를 허용했습니다.

**흐름.** Naruon은 희망·가예약·확정을 구분하고 시간대·소요 시간·준비 여유를 확인합니다. 여행 시간 같은 외부 정보는 유효한 근거가 있을 때만 반영합니다. 근거가 부족하면 ‘충돌 없음’이 아니라 대조 범위를 표시합니다. 개인 일정의 사유는 넘기지 않고 허용된 시간 불가 정보만 씁니다.

**결과와 제외.** 추천 시간과 제한 근거 또는 보류 사유가 제시됩니다. MVP는 읽기만 합니다. 후속 일정 쓰기는 선택된 소스의 capability·승인·ETag 검증이 갖춰진 별도 구현입니다. 실제 일정을 변경하지 않았는데 예약 완료라고 표시하지 않습니다.

**실패와 검증.** 시간대 모호성, 갱신이 오래된 소스, 캘린더 권한 철회, 확정 약속과의 충돌을 검증합니다. E04·E05의 기반은 재사용 후보이며 모든 준비·이동 시간 계산이 이미 있다는 뜻은 아닙니다. 수용 기준: AT11, AT12, AT15, AT18.

## UC07 — 자료의 어디를 읽었고 무엇은 못 읽었는지 확인합니다

**사용자와 시작 조건.** 의뢰에 여러 자료나 같은 이름의 첨부가 있습니다.

**흐름.** 각 조건에서 실제 자료·버전·문단 등의 근거로 이동합니다. 파일명이나 업로드 순서만으로 최신 계약서라고 단정하지 않습니다. 자료의 인식 성공 범위와 원문을 구별합니다. 추출되지 않은 표·이미지·암호화 파일은 확인한 것처럼 조건에 반영하지 않습니다.

**결과와 제외.** 사용자가 근거를 다시 찾는 과정을 줄이는 가설입니다. 파일명을 기준으로 첨부를 합치거나 실패한 변환을 성공으로 감추지 않습니다. 열린 HWPX 미리보기 PR을 전체 HWP 지원으로 홍보하지 않습니다.

**실패와 검증.** 같은 파일명 다른 MIME 파트, 읽을 수 없는 첨부, 삭제·수정된 근거를 검증합니다. E04 및 기존 HWPX 작업을 재사용 후보로만 기록합니다. 수용 기준: AT10, AT13, AT16.

## UC08 — 공동 담당자가 중복 대응하지 않도록 합니다

**사용자와 시작 조건.** 운영자가 권한 있는 보조 담당자에게 특정 의뢰를 맡깁니다. 단일 사용자 MVP 다음 단계입니다.

**흐름.** 사전 설정된 권한과 담당 규칙으로 배정을 제안합니다. 실제 배정 시 서버가 두 사람의 접근 범위와 의뢰 버전을 검증합니다. 담당 변경·보류·수정 이유는 감사 가능하게 남깁니다. 다른 사람이 먼저 처리하면 이전 화면의 변경을 그대로 덮어쓰지 않고 최신 상태를 보여 줍니다.

**결과와 제외.** 담당과 다음 행동이 분명해지지만 담당자로 이름을 붙였다고 전체 메일함의 권한을 주지는 않습니다. 관리자 역할만으로 개인·다른 워크스페이스 자료를 읽게 하지 않습니다.

**실패와 검증.** 동시 점유, 위임 철회, 오래된 UI 응답, 다른 범위의 case UID를 검증합니다. 새 협업 계약으로 취급하며 현재 사용자·조직 필터만으로 완료됐다고 보지 않습니다. 수용 기준: AT12, AT14, AT17.

## UC09 — 수락한 의뢰를 실행할 내부 작업으로 연결합니다

**사용자와 시작 조건.** 사용자가 의뢰 수락을 확인했고, 근거가 있는 산출물·기한이 있습니다.

**흐름.** Naruon은 준비·제작·검수·제출 중 해당 의뢰에 실제 필요한 작업만 제안합니다. 모든 의뢰에 같은 체크리스트를 찍어 내지 않습니다. 허용된 내부 작업 생성 시 의뢰·약속·원문 근거를 연결하고 동일 결정의 재시도로 작업이 중복되지 않게 합니다. 후속 조건 변경은 기존 작업을 조용히 덮어쓰지 않고 변경 제안으로 남깁니다.

**결과와 제외.** 의뢰 수락과 실행 계획 사이의 재입력을 줄일 수 있다는 가설입니다. 내부 작업 생성은 고객에게 수락 메일을 보냈다는 뜻이 아니며 CalDAV 반영도 별도 상태입니다.

**실패와 검증.** 결정 재전송, 동일 UID의 최신 서버 응답, 책임자 변경, 일부 작업 생성 실패를 검증합니다. 기존 Tasks는 재사용 후보 E04이며 합의→작업 변환은 새 설계입니다. 수용 기준: AT09, AT14, AT17, AT19.

## UC10 — 제출과 후속 응답을 끝까지 추적합니다

**사용자와 시작 조건.** 확정된 의뢰에 결과물·증빙·후속 자료 제출의 약속이 남아 있습니다.

**흐름.** Naruon은 무엇을 언제까지 누구에게 제출해야 하는지와 근거를 연결합니다. 준비 완료·전달 요청·공급자 접수·확인 불명·상대 확인을 구별합니다. 외부 쓰기가 없는 초기 단계에서는 사람의 확인과 허용된 원문 증거로 상태를 관리합니다.

**결과와 제외.** 제출 여부를 다시 찾는 부담을 줄일 수 있다는 가설입니다. ‘송금했습니다’라는 메일만으로 입금 완료를 확정하지 않습니다. 회계 장부·세금 판정·추심·수익 예측 기능을 이 제품 범위에 넣지 않습니다.

**실패와 검증.** 반송, 공급자 타임아웃, 첨부 교체, 같은 요청의 중복 처리, 상대 확인 없는 접수만 있는 상태를 검증합니다. 기존 발신 대기 E03·E04는 일부 신호일 뿐 완결된 제출 원장이 아닙니다. 수용 기준: AT07, AT16, AT18, AT19.
